# API Contract — Edge Devices

**Status:** Implemented (backend + edge agent) · dashboard pages pending on the `frontend` branch · companion to [`PRD.md`](./PRD.md) (§0
Glossary, §9 Canonical Defaults) and [`SRS.md`](./SRS.md) (algorithms these endpoints implement).

This is the contract for two different clients:
- **Edge agents** (4 Jetsons) call the `/edge/*` endpoints to report in and fetch config (SRS §3).
- **The dashboard frontend** calls the `/cameras/*` endpoints (new sub-resources on the existing
  camera registry) to build the settings page, device-health widget, and live-view player.

This contract is implemented (see `plans/next-implementation/`). Every JSON body below is specified as a **type table** (field,
type, required, constraints/default) in addition to an example — implement against the table; the
example is illustration, not the spec.

## 0. Conventions (matching the existing codebase)

- All routes are mounted under the existing `/api` prefix (`app/routers/__init__.py:
  APIRouter(prefix="/api")`), same as every existing endpoint — e.g. `GET /api/cameras`. Paths in
  this document omit the prefix for brevity; add `/api` in front of all of them.
- JSON bodies, `snake_case` field names — matches `CameraBase`/`StatusResponse` and every existing
  schema in `app/schemas/`. (The one exception in the current codebase, `build_cctv_detections`,
  returns `camelCase` for historical reasons specific to that one view — **do not** copy that
  pattern for new endpoints.)
- Errors: `{"error": "<message>"}` with a non-2xx status code — matches existing routers
  (`app/routers/cameras.py`). Pydantic validation failures (`422`) use FastAPI's default error
  body shape instead (`{"detail": [...]}"`) — do not wrap those in `{"error": ...}`, that's a
  FastAPI framework behavior, not something to override.
- Success acknowledgements with no meaningful body payload: `{"status": "success"}` — matches
  `app.schemas.common.StatusResponse`.
- Timestamps: ISO 8601 UTC strings, always with an explicit `Z` suffix (e.g.
  `"2026-08-02T14:31:05Z"`) — never a naive/unzoned timestamp.
- IDs generated by the edge (idempotency keys, session correlation) are **UUID v4**, lowercase,
  hyphenated (`"b3f1c9d2-4a11-4e2a-9c3f-7d1e2a6b9f00"`) — reject anything else with `422`.

## 1. Edge-facing endpoints (device → induk)

All four require the device's API key, issued when the device is registered (out of band, by an
admin — SRS §7.3, no self-registration endpoint in this iteration).

```
Authorization: Bearer <device_api_key>
```

Every endpoint in this section: **`401`** on an invalid/revoked key, body
`{"error": "Invalid device credentials"}`. Not repeated per-endpoint below.

### 1.1 `GET /edge/config`

Fetch the device's current authoritative settings. Called on agent startup and whenever a
heartbeat response indicates `config_changed: true` (§1.2, SRS §3.5).

**Response `200` — field reference**

| Field | Type | Notes |
| :--- | :--- | :--- |
| `camera_code` | string | Matches the caller's authenticated device. |
| `yolo_fps` | integer | PRD §9 default 20. |
| `ocr_fps` | integer | PRD §9 default 4. |
| `detect_window_sec` | integer | PRD §9 default 6. |
| `ocr_min_conf` | number (float) | PRD §9 default 0.30. |
| `dedup_iou` | number (float) | PRD §9 default 0.92. |
| `config_version` | integer | Monotonically increasing; the agent stores this as its target `applied_config_version` once applied (SRS §3.5). |

**Response `200` — example**
```json
{
  "camera_code": "GATE-A",
  "yolo_fps": 20,
  "ocr_fps": 4,
  "detect_window_sec": 6,
  "ocr_min_conf": 0.30,
  "dedup_iou": 0.92,
  "config_version": 3
}
```

### 1.2 `POST /edge/heartbeat`

Sent every 30s (PRD §9, SRS §3.5). Updates device health and tells the agent whether it needs to
re-fetch config.

**Request — field reference**

| Field | Type | Required | Constraints |
| :--- | :--- | :--- | :--- |
| `agent_version` | string | yes | Free-form (e.g. semver `"1.0.0"`). |
| `applied_config_version` | integer | yes | The `config_version` this agent last successfully applied (SRS §3.5) — `0` if none applied yet since boot. |
| `local_queue_depth` | integer | yes | `>= 0`. `SELECT COUNT(*) FROM outbox` (SRS §4.1) at send time. |
| `status` | string | yes | One of `"online"` \| `"maintenance"` — never `"offline"` (SRS §5.1: that state is inferred centrally, an agent never claims it about itself). |

**Response `200` — field reference**

| Field | Type | Notes |
| :--- | :--- | :--- |
| `status` | string | Always `"success"`. |
| `config_version` | integer | The induk's current version for this device. |
| `config_changed` | boolean | `true` iff `config_version != <the applied_config_version just received in the request>`. If `true`, the agent must call `GET /edge/config` (§1.1) and apply the new values (SRS §3.5). |

**Response `422`** — request body fails validation (e.g. `status` not one of the two allowed
values) — standard FastAPI/Pydantic error body.

---

### 1.3 `POST /edge/crossings`

Submits one consensus result for a completed Detection Window (SRS §3.2–§3.4).
`multipart/form-data`, since it usually carries a binary snapshot alongside JSON.

**Headers**
```
Authorization: Bearer <device_api_key>
Idempotency-Key: <UUID v4, generated once per crossing, reused on every retry of that same crossing>
```
The agent generates this key once at Window Finalizer time (SRS §3.3) and stores it in the
`outbox` row (SRS §4.1) — it must be the **same** value on every retry of that row, and a **new**
value only for a genuinely new crossing. This is how §5.2's `UNIQUE` constraint de-duplicates.

**Form fields**

| Field | Type | Required | Notes |
| :--- | :--- | :--- | :--- |
| `payload` | text (JSON string) | yes | See table below. |
| `snapshot` | file (`image/jpeg`) | **conditionally** | Required unless `payload.hull_id == "UNKNOWN"` **and** `payload.read_count == 0` (SRS §3.4's empty-window case) — in that one case, omit this field entirely rather than sending a placeholder image. |

**`payload` — field reference**

| Field | Type | Required | Constraints |
| :--- | :--- | :--- | :--- |
| `camera_code` | string | yes | Matches the authenticated device. |
| `detected_at` | string (ISO 8601 UTC) | yes | Detection Window close time (`window_end_ts`, SRS §3.2). |
| `window_sec` | number (float) | yes | Actual elapsed window duration (`window_end_ts - window_start_ts`) — may be less than `detect_window_sec` if closed early by the grace-period path (SRS §3.2). |
| `hull_id` | string | yes | The winning cluster's representative text (SRS §3.3), or `"UNKNOWN"` if `reads` was empty. |
| `confidence` | number (float) | yes | `0.0`–`1.0`. The winning cluster's `share` from `fuzzy_vote_distribution` (SRS §3.3), or `0.0` if `hull_id == "UNKNOWN"`. |
| `read_count` | integer | yes | `>= 0`. `len(reads)` from SRS §3.2 — total OCR reads gathered in the window, before clustering. |
| `votes` | array of objects | yes | May be `[]` iff `read_count == 0`. See below. |

**`votes[]` — field reference** (one entry per consensus cluster, SRS §3.3 step 4, sorted by
`count` descending — matches `fuzzy_vote_distribution`'s own sort order)

| Field | Type | Required | Notes |
| :--- | :--- | :--- | :--- |
| `text` | string | yes | Cluster representative (`distribution[i].id`). |
| `count` | integer | yes | Number of reads in this cluster (`distribution[i].reads`). |
| `avg_ocr_conf` | number (float) | yes | `0.0`–`1.0`. Computed per SRS §3.3 step 3 — **not** returned by `fuzzy_vote_distribution` itself, the agent computes it. |

**`payload` — example**
```json
{
  "camera_code": "GATE-A",
  "detected_at": "2026-08-02T14:31:02Z",
  "window_sec": 5.8,
  "hull_id": "DT-118",
  "confidence": 0.94,
  "read_count": 9,
  "votes": [
    { "text": "DT-118", "count": 6, "avg_ocr_conf": 0.91 },
    { "text": "DT118",  "count": 2, "avg_ocr_conf": 0.85 },
    { "text": "DTI18",  "count": 1, "avg_ocr_conf": 0.62 }
  ]
}
```

**Response `201`** — new crossing accepted:
```json
{ "status": "success", "crossing_id": 4821 }
```

**Response `200`** — `Idempotency-Key` already processed (SRS §5.2) — not an error, returns the
original result:
```json
{ "status": "success", "crossing_id": 4821, "duplicate": true }
```

**Response `422`** — malformed `payload` (fails the field reference table above), or `snapshot`
missing when required, or `Idempotency-Key` header missing/not a UUID v4.

### 1.4 `GET /edge/live-session`

Long-poll control channel for the live-view feature (SRS §8.2–§8.3). The agent keeps this request
open and immediately reissues it on every response.

**Request**
```
GET /edge/live-session?wait=25
Authorization: Bearer <device_api_key>
```

| Query param | Type | Required | Constraints |
| :--- | :--- | :--- | :--- |
| `wait` | integer (seconds) | no | Default `25`. Server holds the connection open up to this long if nothing changes. Server-side max: `30` (reject/clamp higher values rather than error, to tolerate a slightly misconfigured agent). |

**Response `200` — `action: "none"`** (typical case, returned after `wait` elapses with nothing to
report):
```json
{ "action": "none" }
```

**Response `200` — `action: "start"`** (a live session was requested while this poll was open,
returned immediately):

| Field | Type | Notes |
| :--- | :--- | :--- |
| `action` | string | `"start"`. |
| `session_id` | string (UUID v4) | Correlates with the `session_id` the frontend receives from `/live/start` (§2.4) — same value, both sides. |
| `whip_url` | string (URL) | Where to push the WHIP stream. |
| `whip_token` | string | Short-lived, single-use; scoped to this `session_id` only. |

```json
{
  "action": "start",
  "session_id": "b3f1c9d2-4a11-4e2a-9c3f-7d1e2a6b9f00",
  "whip_url": "https://relay.smartgate.example/whip/GATE-A/b3f1c9d2-4a11-4e2a-9c3f-7d1e2a6b9f00",
  "whip_token": "short-lived-token"
}
```
On receiving this, the agent begins pushing its raw camera feed (SRS §8.1 — sourced from the same
ring buffer as detection, no overlay) to `whip_url` using `whip_token`.

**Response `200` — `action: "stop"`** (the active session ended — explicitly or via missed
keep-alive, SRS §8.3 — returned immediately to whichever poll is open):
```json
{ "action": "stop", "session_id": "b3f1c9d2-4a11-4e2a-9c3f-7d1e2a6b9f00" }
```
The agent stops the WHIP push for that `session_id`. If the agent is not currently pushing that
`session_id` (e.g. it already stopped locally for another reason), this is a no-op — never an
error.

## 2. Dashboard-facing endpoints (frontend → induk)

New sub-resources on the existing camera registry (`app/routers/cameras.py`), additive — the
existing `GET`/`POST`/`PUT`/`DELETE /cameras[/{camera_code}]` endpoints are unchanged.

### 2.1 `GET /cameras/{camera_code}/edge-config`

Powers the settings page: current tunables plus device health in one call.

**Response `200` — field reference**

| Field | Type | Notes |
| :--- | :--- | :--- |
| `camera_code` | string | |
| `yolo_fps`, `ocr_fps`, `detect_window_sec`, `ocr_min_conf`, `dedup_iou` | see §1.1 | Current values. |
| `config_version` | integer | Current server-side version. |
| `device_status` | string | `"online"` \| `"offline"` \| `"maintenance"` — SRS §5.1. |
| `agent_version` | string \| null | `null` if the device has never heartbeated. |
| `last_heartbeat_at` | string (ISO 8601) \| null | `null` if never heartbeated. |
| `last_config_applied_at` | string (ISO 8601) \| null | Set when `applied_config_version` last increased. |
| `applied_config_version` | integer | Last version the device confirmed applying (§1.2). |
| `local_queue_depth` | integer | Last-reported value from §1.2. |

`applied_config_version == config_version` is what the UI uses to show "settings saved" vs.
"pending" (SRS §5.3) — if they differ, the device hasn't picked up the latest change yet (check
`device_status`/`last_heartbeat_at` for why).

**Response `200` — example**
```json
{
  "camera_code": "GATE-A",
  "yolo_fps": 20,
  "ocr_fps": 4,
  "detect_window_sec": 6,
  "ocr_min_conf": 0.30,
  "dedup_iou": 0.92,
  "config_version": 3,
  "device_status": "online",
  "agent_version": "1.0.0",
  "last_heartbeat_at": "2026-08-02T14:31:30Z",
  "last_config_applied_at": "2026-08-02T09:12:00Z",
  "applied_config_version": 3,
  "local_queue_depth": 0
}
```

**Response `404`** — unknown `camera_code`: `{"error": "Camera not found"}`

### 2.2 `PUT /cameras/{camera_code}/edge-config`

Operator saves new tunables. Only the device-configurable fields (PRD §9 "Configurable
per-device? Yes" rows) are accepted; this does **not** touch the camera's identity/registry
fields (name, folder, etc. — those stay on the existing `PUT /cameras/{camera_code}`).

**Request — field reference** (all fields optional — partial update, same convention as
`CameraUpdate`; at least one field must be present or the request is a no-op `400`)

| Field | Type | Constraint |
| :--- | :--- | :--- |
| `yolo_fps` | integer | `1`–`30` (expected operating range 18–25, PRD §9) |
| `ocr_fps` | integer | `1`–`15` (expected ~4) |
| `detect_window_sec` | integer | `1`–`30` (expected operating range 5–7) |
| `ocr_min_conf` | number (float) | `0.0`–`1.0` |
| `dedup_iou` | number (float) | `0.0`–`1.0` |

**Request — example**
```json
{ "yolo_fps": 22, "ocr_fps": 5, "detect_window_sec": 5 }
```

A successful write **increments `config_version`** server-side by exactly 1 (SRS §9) — the
response reflects the new version immediately, even though the device won't confirm applying it
until its next heartbeat (SRS §5.3).

**Response `200`** — same shape as §2.1's response, with updated values and incremented
`config_version` (`applied_config_version` unchanged until the device confirms).

**Response `400`** — a value outside its constraint range, or an empty request body:
`{"error": "yolo_fps must be between 1 and 30"}` (one message per first-failing field is
sufficient — no need to aggregate every violation into one response).

**Response `404`** — unknown `camera_code`.

### 2.3 `GET /cameras` (extended)

The existing endpoint (`app/routers/cameras.py: list_cameras`) gains the same health/config
summary fields as §2.1 on each camera row, so the dashboard's device-health widget (SRS §5) can
render all 4 gates from one call instead of 4 separate `edge-config` requests. Existing fields are
unchanged; new fields are additive (`device_status`, `agent_version`, `last_heartbeat_at`,
`local_queue_depth`, `config_version`, `applied_config_version` — same types/notes as §2.1).

**Response `200` — example**
```json
[
  {
    "camera_code": "GATE-A",
    "name": "Gate A — North Checkpoint",
    "gate_location": "North",
    "direction": "both",
    "status": "online",
    "...": "existing camera fields unchanged",
    "device_status": "online",
    "agent_version": "1.0.0",
    "last_heartbeat_at": "2026-08-02T14:31:30Z",
    "local_queue_depth": 0,
    "config_version": 3,
    "applied_config_version": 3
  }
]
```

### 2.4 Live view: `POST /cameras/{camera_code}/live/start`, `/live/heartbeat`, `/live/stop`

Controls one on-demand WebRTC session for a gate's raw camera feed (SRS §8). Raw feed only —
never a detection overlay (PRD Non-Goal, SRS §8.4).

#### `POST /cameras/{camera_code}/live/start`

No request body.

**Response `200` — field reference**

| Field | Type | Notes |
| :--- | :--- | :--- |
| `session_id` | string (UUID v4) | Same value the edge receives via §1.4's `action: "start"`. |
| `whep_url` | string (URL) | The frontend's WHEP-compatible player connects here to play the stream. |

```json
{
  "session_id": "b3f1c9d2-4a11-4e2a-9c3f-7d1e2a6b9f00",
  "whep_url": "https://relay.smartgate.example/whep/GATE-A/b3f1c9d2-4a11-4e2a-9c3f-7d1e2a6b9f00"
}
```

**Session reuse (SRS §8.3)**: if a session for this `camera_code` is already `requested`/`active`,
this endpoint returns that **existing** `session_id`/`whep_url` rather than creating a second,
conflicting one — it is not an error to call `/live/start` twice for the same gate.

If the device is offline, this still returns a `session_id`/`whep_url` (the session enters
`requested` state); streaming won't actually start until the device's long-poll (§1.4) picks it
up. The frontend should treat "no video within a few seconds of a `200`" as "device unreachable,"
not retry this endpoint.

**Response `404`** — unknown `camera_code`.

#### `POST /cameras/{camera_code}/live/heartbeat`

**Request**: `{ "session_id": "b3f1c9d2-..." }` — sent by the frontend roughly every 10s (PRD §9)
while the view is open (SRS §8.3 step 2).

**Response `200`**: `{ "status": "success" }`
**Response `404`** — unknown or already-`ended` `session_id`.

#### `POST /cameras/{camera_code}/live/stop`

**Request**: `{ "session_id": "b3f1c9d2-..." }` — sent when the operator closes the view.

**Response `200`**: `{ "status": "success" }` — idempotent; stopping an already-`ended` session is
not an error.

If no heartbeat arrives for ~20s (PRD §9), the induk ends the session on its own (SRS §8.3 step
4) — the frontend does not need to guarantee `/live/stop` fires on every path (e.g. a crashed
tab), only on the normal close action.

## 3. Frontend surface map

Two distinct frontend surfaces read from this API; how they're split into pages/components is a
frontend decision, but the data they're built from is not — grouped here so both can be built in
parallel without guessing which endpoint belongs where.

### 3.1 Gate dashboard (scoped to one gate/device)
Content: this gate's identity, live device health, current inference settings (with
saved-vs-applied state), this gate's own crossing feed + evidence detail, this gate's ritase
pairing and fleet subset.

| Data | Endpoint |
| :--- | :--- |
| Settings + health for this device | `GET /cameras/{camera_code}/edge-config` |
| Save new settings for this device | `PUT /cameras/{camera_code}/edge-config` |
| Camera identity | `GET /cameras/{camera_code}` |
| This gate's crossings | `GET /crossings?camera_code=` |
| This gate's CCTV detection view | `GET /cctv-detections?camera_code=` |
| This gate's fleet subset | `GET /fleet-registry?camera_code=` |
| This gate's ritase pairing | `GET /ritase?camera_code=` |

### 3.2 Main server (fleet-wide, all 4 gates)
Content: fleet-wide KPIs, all-gates health table, unfiltered crossing feed, shift/daily report,
full fleet registry, camera/device registry management, and the **on-demand live raw CCTV view**
(one gate at a time per viewer, real-time WebRTC, no detection overlay — SRS §8).

| Data | Endpoint |
| :--- | :--- |
| All-gates health table (one call, all 4 devices) | `GET /cameras` (extended, §2.3) |
| Fleet-wide KPIs | `GET /kpis`, `GET /performance-kpis` |
| Unfiltered crossing feed | `GET /crossings` |
| Shift/daily report | `GET /shift-report` |
| Full fleet registry | `GET /fleet-registry` |
| Full ritase reconciliation | `GET /ritase` |
| Camera/device registry CRUD | `POST`/`PUT`/`DELETE /cameras` |
| Start/stop/keep-alive a gate's live raw feed | `POST /cameras/{camera_code}/live/start` `/live/heartbeat` `/live/stop` (§2.4) |

### 3.3 Not a frontend surface
`GET /edge/config`, `POST /edge/heartbeat`, `POST /edge/crossings`, `GET /edge/live-session` are
called by the 4 edge agents, never by the frontend — they're what populates the `device_status` /
`local_queue_depth` / `applied_config_version` fields the surfaces above read, and what makes the
live-view sessions in §3.2 actually start streaming.

## 4. Status code reference (all new endpoints)

| Status | Meaning | Used by |
| :--- | :--- | :--- |
| `200` | Success (read, or a write that doesn't create a new resource) | All `GET`s; `PUT /edge-config`; `POST /edge/heartbeat`; duplicate `POST /edge/crossings`; all `/live/*` |
| `201` | New resource created | `POST /edge/crossings` (new crossing) |
| `400` | Request understood but semantically invalid (e.g. out-of-range value, empty partial-update body) | `PUT /edge-config` |
| `401` | Missing/invalid/revoked device API key | Every `/edge/*` endpoint (§1) |
| `404` | Unknown `camera_code` or unknown `session_id` | `GET`/`PUT /edge-config`, `GET /cameras/{code}`, `/live/heartbeat` |
| `409` | *(reserved, not currently used)* | Not used — session reuse (§2.4) intentionally returns `200` with the existing session rather than `409`, since calling `/live/start` twice for the same gate is an expected, harmless race (e.g. two tabs), not a conflict to reject. |
| `422` | Body fails schema validation (standard FastAPI/Pydantic shape, `{"detail": [...]}"`) | Any endpoint with a request body |

## 5. Open items that affect this contract (see PRD §8 / SRS §11)

- Local footage retrieval (PRD §8's open question #1, SRS §7.2) has no endpoint defined here —
  out of scope until the retention/retrieval approach is decided; it will be a separate
  `/edge/footage`-style endpoint if remote pull (rather than physical retrieval) is chosen. This
  is distinct from the live view in §1.4/§2.4, which is already fully specified.
- Device provisioning/API-key issuance flow is manual for now (SRS §7.3) — no `POST
  /edge/register` endpoint exists in this contract; add one only if the fleet grows past a size
  where manual issuance is impractical.
- Outbox ceiling and local video retention numbers (PRD §9) are proposed defaults pending
  confirmation against the Jetsons' real storage capacity (PRD §8 open question #3) — they don't
  change this API's shape, only the eviction timing behavior an operator might eventually see
  reflected in `local_queue_depth`.
